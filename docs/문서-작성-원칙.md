# 문서 작성 원칙

이 저장소의 문서는 읽는 사람에 따라 두 종류로 나눈다. (사용자 확정 2026-10-14)

- **사용자 가이드** (`docs/guide/`): 프로그램을 실제로 쓰는 사람을 위한 문서. 자연스러운 문장과 실제 사용 예시를 중심으로 쓴다.
- **운영·개발 가이드** (`docs/dev/`, `CLAUDE.md`, `docs/state/`, `docs/HANDOFF.md`): AI에게 개발을 맡기고, 검증 결과를 반영하고, 프로젝트 상태를 관리하는 방법. 명령어와 체크리스트를 적극적으로 써도 된다.

아래 원칙은 사용자 가이드를 쓰거나 고칠 때 적용한다.

## 1. 기본 목표
매뉴얼은 AI나 개발자를 위한 작업 지시서가 아니라 사람이 실제 프로그램을 이해하고 사용하기 위한 문서다. 처음 읽는 사람도 자연스럽게 이해할 수 있게 쓰고, 가독성을 이유로 모든 정보를 표·목록·번호로 바꾸지 않는다.

## 2. 문체
전문적인 소프트웨어 사용 설명서처럼 쓴다. 친절하되 지나치게 설명하거나 독자를 어린아이처럼 대하지 않는다. 자연스러운 한국어 문장을 쓰고, AI 문서에 흔한 기계적인 안내 문구와 반복적인 형식을 피한다. 감탄사, 이모지, 과장된 강조는 쓰지 않는다. 짧은 문장만 나열하지 말고, 필요하면 문장을 이어 읽는 흐름을 만든다.

## 3. 정보 구성
기능을 나열하기 전에 그 기능이 무엇을 해결하는지 설명한다. 독자가 "무엇인가, 언제 쓰는가, 어떻게 쓰는가, 쓰면 어떤 결과가 나오는가"를 알 수 있어야 한다. 단순한 기능은 짧게, 복잡한 기능은 맥락과 실제 예시를 충분히 준다. 모든 기능에 같은 분량을 강제하지 않는다.

## 4. 표 사용
표는 비교하거나 여러 항목을 빠르게 찾을 때만 쓴다. 절차나 개념 설명을 습관적으로 표로 바꾸지 않는다. 두세 문장으로 설명할 수 있으면 문장을 쓴다. 표가 많아 문서가 끊겨 보이지 않게 한다.

## 5. 제목과 강조
제목은 실제 내용을 설명하게 쓴다. '꼭 알아둘 것', '바로 쓰는 말', '이렇게 하세요' 같은 상투적인 제목을 반복하지 않는다. 굵은 글씨는 중요한 용어나 반드시 구분해야 하는 정보에만 쓰고, 한 문단에서 여러 곳을 강조하지 않는다.

## 6. 사용 예시
실제 사용 상황을 중심으로 설명한다. 명령어만 나열하지 말고 어떤 상황에서 쓰는지 함께 적는다. 예시는 복사해 쓸 수 있게 쓰되, 프로그램이 실제로 지원하는 기능만 안내한다. 지원 여부가 확인되지 않은 기능을 구현된 것처럼 쓰지 않는다.

## 7. 기술 용어
일반 사용자가 이해하기 어려운 용어는 처음 나올 때 간단히 설명한다. 내부 모듈명, 개발용 식별자, API 경로, 데이터베이스 구조는 사용자 설명에 불필요하게 드러내지 않는다. 기술적인 세부사항이 필요하면 별도의 참고 문서로 분리한다.

## 8. 문서 구조
프로젝트의 규모와 목적에 맞게 구성한다. 기본적으로 프로그램 소개, 처음 사용하는 방법, 주요 기능과 사용법, 실제 작업 예시, 문제 해결, 참고 정보 순서를 우선 고려하되, 필요 없는 항목은 생략한다.

## 9. 정확성
실제 구현 상태를 기준으로 쓴다. 계획 중인 기능과 구현된 기능을 구분한다. 프로그램이 자동으로 하지 않는 일을 자동으로 한다고 쓰지 않는다. 사용자가 직접 해야 하는 일은 분명하게 안내한다.

## 10. 최종 검토
완성한 뒤 다음을 확인한다. 처음 쓰는 사람이 이해할 수 있는가. 자연스럽게 읽히는가. 표와 목록이 불필요하게 많지 않은가. 같은 설명을 반복하지 않는가. 실제 사용 방법이 충분히 설명되어 있는가. 기술 용어가 과도하게 드러나지 않았는가. 실제 구현과 설명이 일치하는가. 문서의 형식보다 사용자의 이해를 우선한다.
