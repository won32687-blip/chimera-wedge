# 4. 동작 설명

## 한 턴에 일어나는 일
1. **코드**가 지금 단계에서 허용되는 행동 목록(allowed_actions)을 계산한다 (예산·횟수·계열 수 반영).
2. **WEDGE**(공격자 모델)가 그중 하나를 고르고 테스트 입력을 제안한다. 목록 밖 행동이나 형식 오류는 1회 다시 요청, 그래도 틀리면 그 턴을 건너뛴다. 3턴 연속이면 멈춘다.
3. **EXECUTOR**가 허용된 대상인지 확인하고, 예산을 예약한 뒤 대상 프롬프트에 입력을 보낸다.
4. **VERIFIER**가 판정한다: 코드 검사(정규식·길이) → 필요하면 LLM 채점기. 채점기가 FAIL이라고 해도 ① 위반 조건 ID가 명세에 있고 ② 인용문이 실제 응답에 그대로 있을 때만 FAIL로 확정한다. 아니면 INCONCLUSIVE.
5. **CODEX**가 기록한다. FAIL이면 실패(finding)를 만들거나 같은 실패에 연결한다(중복 제거).
6. 새 실패면 **VERIFY**: 같은 입력을 3번 다시 실행해 재현되면 VERIFIED → 회귀 세트.
7. VERIFIED면 **DEEPEN**: 더 짧은 입력으로 같은 실패를 찾는다(최소 실패 입력). 새 정보가 줄면 다른 공격 계열(PIVOT)이나 다음 불변조건(NEXT_INVARIANT)으로 간다.
8. 모든 불변조건이 끝나거나 상한에 닿으면 멈추고 리포트를 쓴다.

## 왜 이렇게 나눴나
- WEDGE는 **제안만** 한다. 판정·검증·예산은 WEDGE가 바꿀 수 없다 → 공격자가 자기 공격을 성공으로 선언하는 일을 막는다.
- VERIFIER에는 WEDGE의 가설·근거를 주지 않는다 → 판정 편향 방지.
- 채점기는 대상과 다른 모델을 쓴다 (같은 모델의 자기 평가는 독립 검증이 아니다).
- 대상 응답은 WEDGE에게 "UNTRUSTED 데이터"로 표시해 전달한다 → 대상 응답 속 지시에 WEDGE가 끌려가지 않게.

## 리포트 읽는 법
- **재현 확인(VERIFIED)**: 확정된 고유 실패 수. 이 숫자가 핵심 결과.
- PENDING·DISPUTED: 한 번 관찰됐지만 재현 확인이 안 된 것. 확정 실패로 세지 않는다.
- 관찰 수: 같은 실패가 몇 번 보였는지 (고유 실패 수와 다르다).
- 비용: 역할(TARGET·WEDGE·JUDGE)별 정산액.
- 검사하지 않은 불변조건: 상한 때문에 못 본 영역. "문제 없음"이 아니다.
